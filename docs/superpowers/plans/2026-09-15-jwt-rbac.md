# LedgerFlow JWT Authentication and RBAC Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Protect LedgerFlow's API with short-lived JWT bearer tokens and enforce the `AUDITOR`, `OPERATOR`, and `TREASURY_ADMIN` permissions at the backend.

**Architecture:** Spring Security runs statelessly. The `/api/auth` controller validates credentials from `app_users`, creates a signed HMAC-SHA256 JWT through Spring Security's JOSE support, and returns a token plus a safe user projection. A request filter decodes bearer JWTs into Spring authorities; `SecurityFilterChain` owns the endpoint authorization policy before controllers or business services execute.

**Tech Stack:** Java 21, Spring Boot 4.1, Spring Security, Spring Security OAuth2 JOSE, PostgreSQL 17, Flyway, JUnit 5, MockMvc, Testcontainers.

**Spec:** `docs/superpowers/specs/2026-09-15-jwt-rbac-design.md`

## Global Constraints

- JWT uses HMAC SHA-256 and a secret supplied by `LEDGERFLOW_JWT_SECRET`, never a committed production secret.
- The JWT secret must be at least 32 bytes; access tokens expire after exactly 30 minutes.
- Passwords are BCrypt-hashed and never appear in a response, error, log, token, or migration.
- Registration always creates `AUDITOR`; public registration must never select a role.
- Public paths are only `POST /api/auth/register`, `POST /api/auth/login`, and `GET /actuator/health`.
- `AUDITOR` is read-only; `OPERATOR` may transfer; `TREASURY_ADMIN` may create accounts and make treasury deposits.
- Missing, expired, malformed, and tampered tokens return the existing safe error shape with HTTP 401; insufficient role returns it with HTTP 403.
- Preserve the current dirty worktree and do not commit or push unless the user explicitly asks.

- [ ] **Step 4: Implement `JwtService` and `AuthService`**

`JwtService.issue` must set subject to `user.getId().toString()`, include string claims `email` and `role`, and set issue/expiry timestamps 30 minutes apart. Use `NimbusJwtEncoder` with `ImmutableSecret<SecurityContext>` and `MacAlgorithm.HS256`; construct a matching `NimbusJwtDecoder` from the same `SecretKey`.

`AuthService.register` lowercases with `Locale.ROOT`, rejects existing email with `ResponseStatusException(HttpStatus.CONFLICT, "Email is already registered")`, BCrypt-encodes the password, creates role `AUDITOR`, and issues a JWT. `AuthService.login` uses `PasswordEncoder.matches`; both nonexistent email and invalid password throw `ResponseStatusException(HttpStatus.UNAUTHORIZED, "Invalid email or password")`.

- [ ] **Step 5: Implement the public auth controller**

```java
@RestController
@RequestMapping("/api/auth")
public class AuthController {
    @PostMapping("/register")
    public ResponseEntity<AuthResponse> register(@Valid @RequestBody RegisterRequest request) {
        return ResponseEntity.status(HttpStatus.CREATED).body(authService.register(request));
    }

    @PostMapping("/login")
    public AuthResponse login(@Valid @RequestBody LoginRequest request) {
        return authService.login(request);
    }
}
```

Configure OAuth2 resource server JWT support using the `JwtDecoder` from `JwtService` and a converter mapping the `role` claim to `new SimpleGrantedAuthority("ROLE_" + role)`.

Configure the authorization matrix:

```java
.requestMatchers(HttpMethod.GET, "/api/**").hasAnyRole("AUDITOR", "OPERATOR", "TREASURY_ADMIN")
.requestMatchers(HttpMethod.POST, "/api/transfers").hasAnyRole("OPERATOR", "TREASURY_ADMIN")
.requestMatchers(HttpMethod.POST, "/api/accounts/*/deposits").hasRole("TREASURY_ADMIN")
.requestMatchers(HttpMethod.POST, "/api/accounts").hasRole("TREASURY_ADMIN")
.anyRequest().denyAll()
```

Use `SessionCreationPolicy.STATELESS`.
